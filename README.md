# git-safe

A lightweight CLI for storing encrypted private files in a Git repository.

- Tracks private files
- Encrypts to `*.safe`
- Manages key access
- Supports SSH and AGE keys

State files:
- `.gitsafe/paths.json`
- `.gitsafe/keys.dat`

Based on the original project:
- https://github.com/erkkah/git-private

## English

### Origin and Key Differences

This project is a reimplementation inspired by:
- https://github.com/erkkah/git-private

Key differences in this codebase:
- New codebase structure (`cmd` + `usecase/ports/adapters`) for cleaner separation and easier testing.
- Git integration uses `go-git` (no runtime dependency on calling `git` executable for repo detection/ignore checks).
- Top-level `generate` command added as shortcut for `keys generate`.
- `hook` command added for transparent workflow:
  - installs `pre-commit` (hide) and `post-merge` (reveal),
  - preserves existing hook content,
  - inserts or updates a managed `git-safe` block.
- Key generation output is simplified:
  - private key file contains raw private key only,
  - public key file contains raw public key only.
- Updated docs and test suite tailored for this reimplementation.

### Quick Start

```bash
# 1) Initialize
git-safe init

# 2) Add your key (SSH example)
git-safe keys add --keyfile ~/.ssh/id_rsa --pubfile ~/.ssh/id_rsa.pub

# 3) Track files
git-safe add .env secrets

# 4) Encrypt
git-safe hide --keyfile ~/.ssh/id_rsa --clean
```

### Commands

```bash
git-safe init
git-safe add <FILE_OR_DIR...>
git-safe remove <FILE...>
git-safe hide [--key KEY] [--keyfile FILE] [--clean] [FILE...]
git-safe reveal [--key KEY] [--keyfile FILE] [--force] [--clean] [FILE...]
git-safe hook [--key KEY] [--keyfile FILE]
git-safe migrate [--dry-run] [--force] [--keep-legacy]
git-safe generate --keyfile FILE [--pubfile FILE]
git-safe clean [--force]
git-safe status

git-safe keys list [--keyfile FILE]
git-safe keys add [--keyfile FILE] [--id ID] [--readonly] <--pubfile FILE | "PUBLIC_KEY">
git-safe keys remove [--keyfile FILE] <--id ID | ID>
git-safe keys generate --keyfile FILE [--pubfile FILE]
```

`generate` is a shortcut for `keys generate`.

`completion` generates a shell autocompletion script (`bash`/`zsh`/`fish`/`powershell`) and works outside a git repository.

### Key Source Priority

For `hide`, `reveal`, and `hook`:
1. `--key`
2. `--keyfile`
3. `GIT_SAFE_KEY` (raw key content)
4. `GIT_SAFE_KEYFILE` (path to key file)
5. `GIT_PRIVATE_KEY` (legacy raw key content)
6. `GIT_PRIVATE_KEYFILE` (legacy path to key file)

For `keys list/add/remove`:
1. `--keyfile`
2. `GIT_SAFE_KEY` (raw key content)
3. `GIT_SAFE_KEYFILE` (path to key file)
4. `GIT_PRIVATE_KEY` (legacy raw key content)
5. `GIT_PRIVATE_KEYFILE` (legacy path to key file)

### Usage Variants (Different Key Types)

#### 1) SSH key pair

```bash
# Add SSH public key to key list
git-safe keys add --keyfile ~/.ssh/id_rsa --pubfile ~/.ssh/id_rsa.pub

# Encrypt/decrypt using SSH private key
git-safe hide --keyfile ~/.ssh/id_rsa
git-safe reveal --keyfile ~/.ssh/id_rsa
```

#### 2) AGE key pair (generated by git-safe)

```bash
# Generate private + public files
git-safe generate --keyfile build/team.age --pubfile build/team.age.pub

# Add AGE public key (AGE requires --id)
git-safe keys add --keyfile build/team.age --id team-main --pubfile build/team.age.pub

# Encrypt/decrypt using AGE private key
git-safe hide --keyfile build/team.age
git-safe reveal --keyfile build/team.age
```

#### 3) Environment variable with key content

```bash
export GIT_SAFE_KEY="$(cat build/team.age)"
git-safe reveal
```

#### 4) Environment variable with key file path

```bash
export GIT_SAFE_KEYFILE=~/.ssh/id_rsa
git-safe hide
git-safe reveal
```

#### 5) Read-only keys for CI users

```bash
git-safe keys add --keyfile ~/.ssh/id_rsa --id ci-bot --readonly --pubfile ./ci.pub
```

### Hook Mode

```bash
git-safe hook
git-safe hook --key "$GIT_SAFE_KEY"
git-safe hook --keyfile ~/.ssh/id_rsa
```

Creates:
- `.git/hooks/pre-commit` -> runs `git-safe hide`
- `.git/hooks/post-merge` -> runs `git-safe reveal`

If a hook already exists, `git-safe hook` preserves its content and inserts or updates a managed `git-safe` block inside it.

Directories passed to `git-safe add` are tracked recursively. Existing files are added immediately, and new files found later in those directories are picked up by `status` and by `hide`. Plain files inside tracked directories are ignored in Git, while `*.safe` files remain visible for commits.

If `--key`, `--keyfile`, `GIT_SAFE_KEY`, and `GIT_SAFE_KEYFILE` are empty,
`git-safe hook` checks legacy `GIT_PRIVATE_KEY` and `GIT_PRIVATE_KEYFILE`, then returns an error and asks to use `--key KEY` or `--keyfile FILE` if no key source is configured.

### Passphrase Warning (Important for Automation)

If your SSH/AGE private key is passphrase-protected, `git-safe` will prompt for passphrase in terminal.
This **can break seamless automation** (hooks, CI/CD, non-interactive pipelines).

Recommendations for automation:
- Use a dedicated automation key without passphrase (restricted scope)
- Store private key in secure CI secrets (`GIT_SAFE_KEY`)
- Use `reveal --clean` in CI jobs

### Legacy Compatibility

New repositories use the native `git-safe` layout:
- state directory: `.gitsafe/`
- tracked file list: `.gitsafe/paths.json`
- encrypted key list: `.gitsafe/keys.dat`
- encrypted files: `*.safe`

Legacy repositories can be converted with:

```bash
git-safe migrate
git-safe migrate --dry-run
git-safe migrate --keep-legacy
```

The legacy repository layout is:
- state directory: `.gitprivate/`
- tracked file list: `.gitprivate/paths.json`
- encrypted key list: `.gitprivate/keys.dat`
- encrypted files: `*.private`

Migration copies encrypted bytes without decrypting or re-encrypting them, so existing keys stay compatible. The old `GIT_PRIVATE_KEY`, `GIT_PRIVATE_KEYFILE`, and `GIT_PRIVATE_DIR` variables are still accepted as fallback aliases where relevant.

### Hook режим

```bash
git-safe hook
git-safe hook --key "$GIT_SAFE_KEY"
git-safe hook --keyfile ~/.ssh/id_rsa
```

Создает:
- `.git/hooks/pre-commit` -> запускает `git-safe hide`
- `.git/hooks/post-merge` -> запускает `git-safe reveal`

Если hook уже существует, `git-safe hook` сохраняет его содержимое и вставляет или обновляет внутри него управляемый блок `git-safe`.

Директории, переданные в `git-safe add`, отслеживаются рекурсивно. Существующие файлы добавляются сразу, а новые файлы в этих директориях подхватываются командами `status` и `hide`. Открытые файлы внутри отслеживаемых директорий игнорируются Git, а `*.safe` остаются видимыми для коммитов.

Если `--key`, `--keyfile`, `GIT_SAFE_KEY` и `GIT_SAFE_KEYFILE` не заданы,
`git-safe hook` проверит legacy-переменные `GIT_PRIVATE_KEY` и `GIT_PRIVATE_KEYFILE`, затем вернет ошибку и попросит использовать `--key KEY` или `--keyfile FILE`, если источник ключа не настроен.

### Важно: passphrase и автоматизация

Если приватный SSH/AGE ключ защищен паролем (passphrase), `git-safe` запросит ввод в терминале.
Это **может ломать бесшовную автоматизацию** (хуки, CI/CD, неинтерактивные процессы).

Рекомендации для автоматизации:
- использовать отдельный automation-ключ без passphrase (с ограниченными правами)
- хранить приватный ключ в секрете CI (`GIT_SAFE_KEY`)
- в CI использовать `reveal --clean`

### Legacy-совместимость

Новые репозитории используют native-layout `git-safe`:
- директория состояния: `.gitsafe/`
- список tracked-файлов: `.gitsafe/paths.json`
- зашифрованный список ключей: `.gitsafe/keys.dat`
- зашифрованные файлы: `*.safe`

Legacy-репозитории можно конвертировать командой:

```bash
git-safe migrate
git-safe migrate --dry-run
git-safe migrate --keep-legacy
```

Legacy-layout репозитория:
- директория состояния: `.gitprivate/`
- список tracked-файлов: `.gitprivate/paths.json`
- зашифрованный список ключей: `.gitprivate/keys.dat`
- зашифрованные файлы: `*.private`

Миграция копирует зашифрованные байты без расшифровки и повторного шифрования, поэтому существующие ключи остаются совместимыми. Старые переменные `GIT_PRIVATE_KEY`, `GIT_PRIVATE_KEYFILE` и `GIT_PRIVATE_DIR` по-прежнему поддерживаются как fallback-алиасы там, где это применимо.
